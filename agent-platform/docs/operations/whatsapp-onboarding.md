# WhatsApp Cloud API onboarding

This runbook activates one Meta WhatsApp Cloud API number for one persisted agent route. It does not use environment variables for provider credentials and does not expose the unkeyed legacy webhook.

## Current production status

As of 2026-08-31, production has no persisted WhatsApp channel connection and no WhatsApp agent route. The platform is therefore **not WhatsApp-ready** until this runbook is completed and a real Meta canary succeeds.

The intended callback is:

```text
https://agent.saltacode.com.ar/webhooks/whatsapp/saltacode-main
```

## Activation gates

Do not configure the public Meta callback until all of these are true:

- The target agent is selected, active, and has a working persisted runtime/provider configuration.
- The release containing the durable WhatsApp inbox migration and worker has been merged and deployed, the migration is at head, and the worker is healthy. A webhook HTTP `200` only proves acceptance; durable processing depends on this worker.
- The operator has panel permissions to manage shared connections, agent routes, and WhatsApp access.
- Meta provides the WhatsApp Business Account/number, exact `phone_number_id`, an appropriate permanent access token, and the application secret.
- A strong, unique verify token has been generated by the operator and stored in the approved password manager.
- The test sender is allowed both by Meta when the application is in test mode and by the selected agent's WhatsApp access policy.

Never send access tokens, verify tokens, app secrets, screenshots containing them, or exported credential payloads through chat, issues, commits, logs, or shell command arguments. Paste them directly into the panel password fields. The panel stores them encrypted and returns only credential readiness; it cannot reveal them later.

## 1. Create the shared channel connection

Open the panel at `/shared/channel-connections`, choose **Nueva conexión**, and enter:

| Field | Value |
|---|---|
| Name | A clear operational name, for example `SaltaCode WhatsApp` |
| Slug | A stable shared identifier, for example `saltacode-whatsapp` |
| Channel | `WhatsApp` |
| External account ID | The exact Meta `phone_number_id` |
| Access token | The permanent Meta access token |
| Verify token | The operator-generated token that will also be entered in Meta |
| App secret | The Meta application secret |
| Configuration JSON | `{}` unless a reviewed non-secret setting is required |
| Active | Enabled |

`external_account_id` is not the display phone number, WhatsApp Business Account ID, or application ID. It must equal the `phone_number_id` included by Meta in webhook payload metadata; mismatches are rejected.

All three credential fields are required together for creation or rotation. When editing, leaving all three empty preserves the encrypted credential. Never place secrets in **Configuration JSON**.

After saving, confirm that the connection is active and reports **Configurada (write-only)**. This is storage evidence, not provider connectivity evidence.

## 2. Bind the selected agent route

Select the intended agent, open **Canales**, choose **Nueva ruta**, and enter:

| Field | Value |
|---|---|
| Channel | `WhatsApp` |
| Route key | `saltacode-main` |
| Connection | The shared connection created above |

Keep the route active. The route key is a public routing identifier, not a secret. It resolves exactly one active agent and one active WhatsApp connection.

Do not configure Meta against `/webhooks/whatsapp`; that unkeyed endpoint is legacy compatibility only and cannot guarantee multi-agent ownership.

## 3. Authorize the canary sender

With the same agent selected, open **Acceso WhatsApp** and create or reuse the canary identity:

1. Enter the sender phone in international digits, without spaces or punctuation.
2. Assign it to the selected agent.
3. Enable **Acceso activo**.
4. Grant only the document areas required for the canary; area access is independent from permission to send a message.

This is the platform access policy. If Meta is still in test/development mode, also add the same recipient or sender wherever Meta requires test-number authorization.

## 4. Configure Meta Webhooks

In the Meta application that owns the WhatsApp number:

1. Set the callback URL to `https://agent.saltacode.com.ar/webhooks/whatsapp/saltacode-main`.
2. Enter the same verify token stored in the shared channel connection.
3. Complete Meta's callback verification. Meta performs a `GET`; success returns its challenge as plain text. A wrong token returns `403`, while an inactive or incomplete persisted route returns `503`.
4. Subscribe the WhatsApp Business Account to the `messages` webhook field so inbound messages and outbound delivery-status callbacks reach the keyed route.

Do not reproduce the verification token in a `curl` command or paste it into an incident transcript. Use Meta's verification flow. Repository tests cover synthetic GET/POST verification; production POST proof must come from a real Meta-signed callback. The keyed POST path verifies the exact request-body signature with the stored app secret and rejects a different `phone_number_id`.

Meta references:

- [WhatsApp Cloud API overview](https://developers.facebook.com/docs/whatsapp/cloud-api/)
- [WhatsApp Cloud API webhooks](https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/)

## 5. Run the real canary

Use only the authorized test phone and send one unique, non-sensitive text message to the business number.

The canary passes only when all of the following evidence exists:

1. Meta's signed POST is acknowledged without retry or authentication errors.
2. The durable inbox accepts the event and the worker completes it once; a duplicate provider message ID does not generate a second reply.
3. The user receives the agent response on WhatsApp.
4. **Conversaciones** for the selected agent shows the WhatsApp conversation, the `saltacode-main` route, the expected principal, and both message directions.
5. **Auditoría** for the selected agent records the execution with non-null agent and channel-route ownership and contains no credential material.
6. Delivery tracking correlates the returned Meta message ID and progresses beyond API acceptance to `delivered`; after the user opens the reply it should reach `read`. A send API `200` or `sent` status alone does not prove delivery.

Record timestamps, route/connection identifiers, redacted Meta message IDs, conversation/audit identifiers, and final delivery state. Do not retain message contents or phone numbers outside the approved operational evidence location unless required for the incident.

## Failure interpretation

| Evidence | Likely boundary |
|---|---|
| Meta callback verification returns `403` | Verify token differs from the write-only value stored in the connection. |
| Verification or POST returns `503` | Route/connection is absent, inactive, incomplete, undecryptable, or the durable inbox cannot accept the message. |
| POST returns `401` | Meta signature is absent or does not match the stored app secret. |
| POST returns `403` after signature validation | Payload `phone_number_id` differs from `external_account_id`. |
| POST is accepted but there is no completed inbox job | Worker, migration, database, or retry/dead-letter path is not healthy. |
| Reply is accepted by Meta but not delivered | Inspect the correlated delivery status and provider error; do not classify API acceptance as delivery. |
| Access is denied | Verify the identity is active for the selected agent, not merely present in the shared identity library. |

## Reversible rollback

1. In the selected agent's **Canales** page, deactivate the `saltacode-main` route. This immediately prevents the callback from resolving an active runtime.
2. If the shared WhatsApp connection is not used by another route, deactivate it as a second containment step.
3. Preserve conversations, audit records, delivery statuses, inbox jobs, and the connection record for diagnosis. Do not delete or rewrite persisted history.
4. After containment, investigate and release a forward fix. Re-enable the connection first and the route last, then repeat the real Meta canary.

Credential rotation is not the normal rollback. Rotate only when compromise or provider policy requires it, and update all three write-only credential fields together.

## Completion record

WhatsApp production readiness may be declared only after the real Meta canary passes. Keep a redacted operator record containing:

- release and database migration revision;
- durable inbox worker health;
- selected agent, connection ID, channel-route ID, and route key;
- Meta application/number identifiers without credentials;
- GET verification timestamp;
- inbound, reply, conversation, audit, and `delivered`/`read` evidence;
- operator and rollback decision, if any.
